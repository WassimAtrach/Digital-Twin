A traffic-light network, built to be attacked

A working simulation of five traffic-light junctions, controlled by an AI that decides which light turns green from live sensor data. Next to it, a console that attacks the system using real, documented security weaknesses, not made-up ones, and shows how it defends against them.

Junctions 5

The five junctions use real Tel Aviv street names, and two are based on real, published traffic numbers. One of the attacks modeled here is the same weakness researchers found in real traffic controllers in 2014 (source). Every attack is labeled with its official classification from MITRE's attack catalog for industrial systems.

What's worth knowing about how it works

The interesting decisions, explained plainly

No shortcuts for "trusted" traffic backend

The real AI and a separate tool built just to attack the system send their requests through the exact same two functions. There's no secret backdoor that skips the security check for traffic the system already trusts. The only thing that decides if a request is allowed is whether it's signed correctly. Real or fake, they're treated exactly the same way, which is what makes the security actually mean something instead of just being for show.

Messages that stop working if they're reused backend

Every command is signed with a secret key, and the exact time it was sent is part of what gets signed. If someone captures a real message and tries to send it again later (this is called a replay attack), it gets rejected for being too old, even though the signature itself is still technically valid. 

if abs(time.time() - timestamp) > FRESHNESS_WINDOW_SECONDS:
    return False  # a real, valid signature -- just sent too long ago
return hmac.compare_digest(signature, expected)

A second check that doesn't trust the first one backend

Even a command that's perfectly signed and looks completely legitimate still passes through one more independent check before it's allowed to do anything dangerous. It's modeled on a real piece of hardware traffic cabinets actually have: a physical backup device that can override the computer if it ever tries to show conflicting green lights. One broken piece isn't supposed to be enough to cause real damage.

A small prediction model that keeps learning backend

One shared model guesses how much traffic is about to show up at each junction, and it keeps learning the whole time the server is running. It's not trained once and left alone. I built it from scratch instead of using a library, so I can explain every part of it. It also learns from every sensor reading it receives, real or faked, which means a fake traffic report doesn't just lie about one number. It can actually shift what the model expects going forward.

Tested by attacking it, not by reading the code testing

I checked my own work by actually attacking the running server: sending broken requests on purpose, opening 210 real connections at once to check a limit actually holds, and using a real browser to click through the site automatically to catch things an API test alone would miss. When a fix worked, I proved it by running the exact same attack again and watching it fail.

Two real bugs I found by breaking my own system

Both were caught by testing, not by reading the code back later

One fake traffic report broke predictions at all five junctions

The prediction model is shared across every junction, so it learns faster with less data. That backfired: I sent one obviously fake, huge traffic number as a test, and it didn't just mess up the junction I targeted. It broke the model's guesses everywhere, since they all come from the same shared model. I found this myself, then fixed it by putting a sensible limit on how large a single report is allowed to be.

✓ Reproduced it, fixed it, then confirmed the same attack no longer breaks it
A button called "Isolate Node" didn't actually isolate anything

It said, right there in its own description, that it would cut a junction off from all incoming traffic. I tested that claim directly: isolated a junction, then attacked it again right away, and the attack still worked. The code that was supposed to block traffic to an isolated junction existed, but was never actually being checked anywhere.

✓ Found by testing what the button claimed to do, not trusting the label

How it's put together

Security

Two separate locked channels, one for commands and one for sensor data, each protected against messages being captured and resent later, plus a system that auto-blocks repeat attackers and a backup check that trusts nothing above it.

The AI

Decides which direction gets the green light by looking at how much traffic is currently waiting, plus a short-term prediction of what's about to arrive.

Simulation

A fake camera network that generates realistic traffic, with each junction tuned to real research on how busy that specific street actually is.

The dashboards

Two live pages that update instantly as things happen, one built around attacking and defending, the other showing all five junctions at once.

Stack

Python FastAPI asyncio WebSockets HMAC-SHA256 vanilla JS (no framework) HTML5 Canvas a prediction model built from scratch no database, by design
