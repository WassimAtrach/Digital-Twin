A digital twin, built to be attacked

Full-stack · applied security · applied ML — solo project

A working digital twin of a five-junction traffic-signal network — an AI that times the lights from live sensor data, and a real attack console that demonstrates documented, published ICS vulnerabilities against it, not invented ones.

Most "security demo" projects invent a toy vulnerability to patch. This one doesn't: the attack it opens with — an unauthenticated command channel — is the exact weakness University of Michigan researchers found in real production traffic controllers in 2014 ("Green Lights Forever"). The five junctions carry real Tel Aviv street names, and two of them are backed by genuine, cited traffic-volume research — including a real intersection ITC (the Israeli traffic-tech company this project is modeled on) told ynet it actually manages. Every attack is tagged with its real MITRE ATT&CK for ICS technique. Nothing here is dressed up to look researched — it's built from what's actually published.

Technical highlights

What's actually interesting under the hood

No special "trusted" code path architecture

The legitimate AI orchestrator and a standalone CLI attacker call the exact same two functions to submit a command or a sensor reading. There's no internal shortcut that skips authentication for "trusted" traffic — the only thing that distinguishes a real signal from an attack is whether the request carries a valid signature. That symmetry is what makes the security model provable rather than asserted.

Replay-resistant signing, not just "has a password" security

Commands and telemetry are HMAC-SHA256 signed with the timestamp folded into the signed payload — not carried alongside it, which would let a captured signature be replayed with a forged fresh timestamp. Comparison uses a constant-time check to close the timing side-channel a naive == would leak. 

if abs(time.time() - timestamp) > FRESHNESS_WINDOW_SECONDS:
    return False  # mathematically valid signature, but too old
return hmac.compare_digest(signature, expected)

Defense in depth, modeled on real hardware security

A software Conflict Monitor runs after signature verification, standing in for the physical Malfunction Management Unit real traffic cabinets wire between the controller and the lamps — it vetoes a dangerous command even if the signature was completely valid. One compromised layer doesn't cascade into a dangerous outcome by itself.

A live-learning ML model, hand-rolled and explainable ML

One shared linear regression model forecasts near-term arrivals for every junction, trained online via gradient descent for as long as the server runs — no pre-baked dataset. Built from scratch rather than pulling in a library, so the prediction step is a single, fully readable dot product. It also trains on every accepted sensor reading, forged ones included, which means a data-poisoning attack doesn't just distort one number — it measurably nudges what the model has learned.

Tested by attacking it, not by reading it rigor

Verification throughout meant firing real traffic at the live server — malformed requests, 210 genuine concurrent WebSocket connections to prove a connection cap actually holds, headless- browser automation clicking real buttons to catch bugs an API test alone would miss. Fixes were re-tested against the exact same live reproduction that found the bug, not assumed correct from the diff.

Real bugs, found by breaking my own system

Two, condensed. Both were found live, not by code review.

One forged sensor reading corrupted the AI across all five junctions

Because the forecasting model is shared across every junction for better generalization, a single extreme value sent as one "vehicle count" became a training target that blew out the model's weights network-wide — not just at the junction it targeted. Root-caused to plain gradient descent's lack of built-in resistance to a single outlier, then capped what can actually reach the training step.

✓ Reproduced live, fixed, re-verified against the same attack
The button called "Isolate Node" never actually isolated anything

Its own tooltip promised it would cut a junction off from all traffic. Isolating a junction and immediately re-attacking it directly proved otherwise — the flag that marked a junction isolated was being set, but never actually checked against incoming requests anywhere.

✓ Found by testing the real claim, not trusting the label

Architecture, briefly

Security

Two independently-keyed signed channels, freshness-windowed against replay, an auto-blocking threat tracker, and a conflict monitor that trusts nothing above it.

Intelligence

An orchestrator that scores real-time queues plus the ML model's forecast to time each signal, including gap-out early-termination logic from real actuated-signal-control practice.

Simulation

A camera network generating realistic, weighted arrival events, calibrated per junction from cited real-world traffic research.

Interface

Two live dashboards over one WebSocket feed — a SOC-style attack console with a guided incident-response playbook, and a five-junction live monitor.

Stack

Python FastAPI asyncio WebSockets HMAC-SHA256 vanilla JS (no framework) HTML5 Canvas hand-rolled online SGD no database, by design
